# MCP 性能基线与后续改进

2026-09-05，在 Apple M3 / macOS arm64 / Node v22.12.0 上采集。

执行 `npm run benchmark:mcp` 可重跑。脚本在独立子进程中分别测试 100、500 帧，使用临时项目，结束后删除素材。原始数据见同目录 `mcp-baseline-2026-09-05.json`。

## 工作负载与测量范围

- 每帧为同一张确定性生成的 512×512 PNG：中央带纹理的不透明主体，外围透明；每张 PNG 340409 字节。
- 经过真实 STDIO 请求解析、`tools/call`、公开 `callMcp`、导入和摘要读取流程。
- FFmpeg 提取替换为复制预生成 PNG；导入耗时包括这段复制时间。没有测视频解码、GIF 编码、Florence 推理或真实素材视觉质量。
- 导入和紧接其后的 ping 各测一次；摘要在预热后测三次。内存是每个独立进程的峰值 RSS，包含生成素材、服务加载、导入和读取等阶段。
- 全量 PNG 读取次数通过 `fs.readFileSync` 计数，包含页面缓存命中；不能将逻辑读取量当作物理磁盘吞吐。

## 结论与推荐顺序

1. **先消除磁盘帧转 base64 的往返。** 视频已提取出 PNG，但导入仍把所有帧装成 base64 列表，再解码回字节。建议让导入模块支持文件路径，按帧处理。以同一基准比较峰值 RSS、导入耗时与最终 PNG 哈希，不能用本次基线预先承诺收益。
2. **再改善长任务期间的控制消息响应。** 当前传输队列使 ping 等待前一个工具，业务执行也有序排队。仅把 ping 移出队列无法解决同步哈希和像素运算阻塞事件循环的问题；需要一起评估异步文件处理或 worker，同时保留写操作的有序性和快照检查。
3. **保留观察前后校验，先减少重复成本。** 摘要调用前后各对全部帧读取并哈希；这是检测外部修改的现有保证。不能直接删除第二遍，也不能仅用 mtime/size 替代内容依据。评估请求内复用、流式读取或受版本控制的数据存储后，再决定缓存策略。
4. **按上述职责逐步整理模块。** 当前已独立出文件事务和参数校验；下一处有具体依据的是导入模块。等清楚其输入、资源生命周期和验证方式后再拆，不按文件行数批量搬代码。

本轮只建立性能基线，未改变生产请求调度、哈希策略或视频导入实现。以上是待实施方向，不是性能优化完成声明。
